## 1. 降低 AI 开发错误（最高优先级维度）

两份文档的核心判断一致且正确，直接采纳：

**错误暴露层级阶梯**（rust 文档 §3.1）：

```
层级A 运行时（最晚）  ← 后端现状：4115 行纯 JS，错误要等 npm test 或真机才现形
层级B 编译期（严格TS） ← tsc 报错具体可定位，AI 就地自纠
层级C 编译期+所有权    ← Rust：额外拦数据竞争/悬垂，但编译循环慢、AI 初始错误率更高
```

**本项目 5 类真实错误源**（rust 文档 §2.3）：E1 跨模块字段漂移、E2 前后端契约漂移、E3 静默吞错、E4 LLM 输出不可控、E5 外部 API 异构。其中 **E4/E5（动态边界）占了错误面的大头，而这恰是 Rust 覆盖不了的**——它只能 `serde_json::Value` 容错，与"需要宽松容错"的边界需求方向相反。

### 1.1 剩余行动（按杠杆排序）

**A1. 后端类型化启动（O-5，两份文档共同的第一杠杆，预计收益 80% 的"编译器闸门"）**

渐进三步，每步独立可回滚：
1. 新增 `tsconfig.server.json`：`allowJs:true + checkJs:true`，先只对 `store.js`/`metrics.js`/`llm.js` 三个核心文件开 `// @ts-check`；
2. 关键模块补 JSDoc `@param/@returns/@typedef`，让 checkJs 报错收敛；
3. `package.json` 的 `typecheck` 改为 `tsc --noEmit && tsc -p tsconfig.server.json`，CI 双闸门。

**A2. zod 边界校验（rust 文档方案 A 的另一半，覆盖 E4/E5）**

只在四个动态边界加 schema，不做全量：
- `llm.js`：`extractFirstJson` 之后（triage/schedule/summarize 的输出结构）；
- `sources.js`：Zotero `Total-Results` 分页头、OpenAlex `cited_by_count` 类型校验已有雏形，统一为 zod parse + 语义化降级；
- `routes/api.js`：请求体（替代 4 处 `try{json()}catch{}`）；
- `store.js`：`readJson` 的文档结构（version/entries 等）。

**A3. 清理静默吞错（O-13 + E3）**
`routes/api.js` 7 处空 `catch {}` 至少补 `ctx.log?.warn` 或语义化 400 响应；`createStore(dataDir)` 模块级 memoize（`Map<dataDir, store>`），消除多实例隐患。

**A4. triage 乱序水位线（O-12）**
`pending` 先按 `createdAt` 升序排序再取最早批次，补录条目不再被永久跳过；保留现有 T6 同毫秒判重测试。

### 1.2 Rust 取舍判断（同意 rust 文档结论）

- **不做全栈 Rust 重构**：错误杠杆方向对（前移编译期）但工具选错——覆盖不了 E4/E5 动态边界，且放大 AI 正确率最低的层（前端 WASM、借用检查）。
- **可选保留 metrics/parsers 的 Rust PoC**（方案 B）：作为"AI 自纠循环质量"的对照实验，排在 A1/A2 之后，不承诺生产收益，改挂 JS 即可回退。
- **性能视角佐证**（见 §2）：本插件工作负载是 I/O bound，Rust 在 CPU 侧几乎无收益，进一步削弱重构动机。

## 2. 性能分析（两份文档均未覆盖，本文档增量）

### 2.1 工作负载画像

| 层 | 负载类型 | 瓶颈 |
|---|---|---|
| `sources.js`（Zotero/OpenAlex） | 网络 I/O，分页顺序抓取，`cacheTtlMs: 0` 零缓存 | 延迟大头 |
| `llm.js`（triage/建议/摘要） | LLM 调用，秒级 | 延迟大头 |
| `store.js` | **同步** fs I/O + 双写放大 | 事件循环阻塞源 |
| `metrics/parsers` | 纯函数，小数据量 | 无瓶颈（Rust 化无性能意义） |

**总体判断**：CPU 从来不是瓶颈，延迟由网络/LLM 主导，事件循环偶发阻塞来自同步 fs。任何语言级重写（含 Rust）对本插件的体感性能收益 ≈ 0——这从性能维度再次佐证 rust 文档"不为此重构"的结论。

### 2.2 store.js 写放大与读开销（实测代码证据）

每次 `store.update` 的实际成本：
1. `JSON.stringify(doc, null, 2)` **pretty-print**（文件体积约翻倍）→ 主文件原子写（tmp + rename，这部分设计正确）；
2. **再** `JSON.stringify` + 写一份快照（`store.js:134/180/212` 三条 update 路径都调 `snapshot()`）——即每次更新 = 2 次全量序列化 + 2 次磁盘写，快照**无节流**；
3. 快照保留 20 份，prune 为 readdir + sort + unlink。

读取侧：无内存缓存，每次 `store.read` = `readFileSync` + `JSON.parse` 全量解析（O-13 文档已确认"当前无内存缓存"）。

**建议（低急迫、高确定性）**：
- **读缓存**：`createStore` 内维护 `Map<name, {version, doc}>`，`read` 命中且磁盘 mtime 未变则直接返回；`update` 后失效——消除高频 read 的重复解析；
- **快照节流**：同 version 或 N 秒内只写一份快照（快照本身是回退保险，不需要每次 update 都落盘）；
- **序列化去 pretty**：主文件 `JSON.stringify(data)` 无缩进（导出路径已有独立渲染，不影响可读性需求）；快照同理。

### 2.3 sources.js 网络侧

- `cacheTtlMs: 0`（`sources.js:57/100/599`）：Zotero/OpenAlex 响应完全无缓存，30 分钟轮询每次全量重抓。建议对 OpenAlex 引用数等慢变数据加 24h TTL，对 Zotero 列表加 30min TTL（与轮询周期对齐）；
- 分页抓取未见 `Promise.all`：可改为有界并发（如 p-limit 3），遵守 Zotero 速率限制的同时缩短同步窗口。

### 2.4 前端

React 19 + Vite，3048 行，规模健康；O-14 完成后类型边界已收紧，无渲染性能问题的证据。不投入。

## 4. 三合一路线图（最终优先级）

| 波次 | 项 | 主维度 | 预期效果 |
|---|---|---|---|
| **Wave 1** | A1 后端类型化启动（tsconfig.server.json + 3 核心文件） | AI 错误 | E1/E2 类错误前移到编译期 |
| **Wave 1** | A2 zod 四边界 | AI 错误 | E4/E5 类错误从"静默 undefined"变"显式降级" |
| **Wave 2** | A3 空 catch 清理 + createStore memoize | 质量+性能 | 可观测性 + 消除多实例 |
| **Wave 2** | A4 triage 水位线排序 | 质量 | 补录不漏巡检 |
| **Wave 2** | store 读缓存 + 快照节流 + 去 pretty | 性能 | 消除事件循环阻塞源与写放大 |
| **Wave 3** | Biome lint、O-11 CSV、O-6 harness 收尾 | 质量 | CI 三闸门（test/typecheck/lint） |
| **Wave 3** | sources TTL 缓存 + 有界并发 | 性能 | 缩短同步窗口 |
| **可选** | metrics Rust PoC（rust 文档方案 B） | 研究性 | 验证 AI 自纠循环，非生产收益 |

每波验收：`npm test`（12 套）全绿 + `npm run typecheck` + `npm run build:server`；行为类改动（prompt/LLM 边界）跑 mock 用例 + 真实 LLM 抽样 2–3 次。

## 5. 底线判断

1. **剩余最高杠杆不是 Rust，是"后端 TS 化 + zod 边界"**——两份文档结论一致，且经源码复核确认这两项恰好是唯一没做的高优先级项；
2. **性能上这个插件没有系统性问题**：I/O bound 架构，瓶颈在网络与 LLM；store.js 的同步双写是唯一值得修的本地热点，语言重写无收益；
3. **Rust 判定维持 rust 文档结论**：仅作 metrics/parsers 的可选 PoC，排在所有 TS/zod/性能项之后；
4. 原优化方案 14 项已完成 9.5 项，剩余 4.5 项（O-5/O-11/O-12/O-13 + O-6 尾巴）全部纳入上文路线图。
