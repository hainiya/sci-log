## 1. P0 —— 正确性缺陷（必须修复）

### 1.1 O-1 `tools/log-work.js`：nextStepAdvice 上下文重复追加

- **定位**：`src-server/tools/log-work.js` 第 213–218 行。
- **问题**：step 3（第 137 行）已 `store.update("worklog", ...)` 把 `worklogEntry` 写入 store；step 6 又做 `entries: [...store.read("worklog").entries, worklogEntry]`，而此刻 `store.read("worklog").entries` **已含** `worklogEntry`，导致传给 `nextStepAdvice` 的 worklog 里该条目出现两次。
- **影响**：LLM 看到的「刚记录的新条目」重复出现，可能把同一条记录当作两条来评估，污染"下一步建议"。
- **方案**：

```js
// 旧
const worklogWithNew = {
  ...store.read("worklog"),
  entries: [...(store.read("worklog").entries || []), worklogEntry],
};
// 新：step3 已写入，read 即最新，无需（也不应）再手动追加
const worklogWithNew = store.read("worklog");
```

- **收益**：消除上下文重复；无副作用（`nextStepAdvice` 本身只读不写库）。
- **风险**：极低。
- **工作量**：约 5 分钟。建议加一条回归测试（见 O-6）。

### 1.2 O-2 版本号不一致

- **定位**：`package.json`（`0.1.0`）vs `manifest.json`（`0.2.0`），且 `sources.js` 的 `ZOTERO_UA = "materials-research-copilot/0.1.0"` 亦硬编码。
- **影响**：发布/调试/UA 三处版本语境不统一，易误导。
- **方案**：
  - 以 `package.json` 为单一版本源；`manifest.json` 的 `version` 改为构建时注入，或加 `scripts/sync-version.mjs` 校验两边相等（构建失败即前者同步）。
  - `ZOTERO_UA` 改为从 `package.json` 读 `version`（`build:server` 已用 esbuild，可用 `--define` 注入，或直接 `import pkg from '../package.json'`）。
- **收益**：版本单一可信。
- **风险**：低。
- **工作量**：小。

### 1.3 O-3 prompts 与代码脱节

- **定位**：
  - `prompts/worklog-triage.md`：仍要求参照「研究方案（题目/假设/路线/里程碑）」并输出 `planNote / needRedo / redoReason`，但 `llm.js.triageWorkEntry` 已删这些字段（git `5c00d2c` "drop unused triage fields"）且**不再传研究方案进 docs**（docs 只有 today/实验记录/甘特/文献库）。
  - `prompts/next-step-advisor.md`：输入章节列「研究方案」，但 `nextStepAdvice` 只传 `worklog/gantt/calendar`。
  - `prompts/worklog-generate.md`：`{{MESSAGE}}` 占位符**从未被替换**（`generateDraft` 把整个 prompt 作 `system`，把 `msg` 作 `user`，`{{MESSAGE}}` 字面留在 system）。
- **影响**：提示词让 LLM 去做"有输入但缺失"的任务，或见到未替换的模板残片，易诱发困惑/编造；对行为塑造类内容影响最大，需按仓库"skill 改动需 eval"标准审慎处理。
- **方案**：
  1. `worklog-triage.md`：删「研究方案」输入章节，删 `planNote/needRedo/redoReason` 字段与对应规则；`system` 枚举保持与 `metrics.js SYSTEM_DEFS` 一致。
  2. `next-step-advisor.md`：删「研究方案」条目。
  3. `worklog-generate.md`：二选一——(a) 去掉 `{{MESSAGE}}`，明确"消息由调用方以 user 角色提供"；或 (b) `generateDraft` 里 `base.replace(/\{\{MESSAGE\}\}/g, msg)` 后再拆 system/user，让模板真正可用。推荐 (a) 更贴近现状。
- **收益**：提示词与实现一致，AI 行为可预期。
- **风险**：提示词改动会改变 LLM 输出，**建议在改动后跑 `sources.test`/`worklog-gen.test` 的 mock 用例，并对真实 LLM 做 2–3 次抽样**（仓库要求行为改动需验证）。
- **工作量**：中。

## 2. P1 —— 可维护性与可靠性

### 2.1 O-4 export 渲染 / safeName 重复

- **定位**：`routes/export.js` 与 `tools/export-report.js` 的 `safeName()` 与「实验记录 Markdown 渲染」逻辑几乎逐字相同。
- **方案**：抽 `src-server/server/export-util.js`：

```js
export function safeName(value) { /* 原实现 */ }
export function renderWorklogMarkdown(entries) { /* 原实现 */ }
```

两处改为 `import { safeName, renderWorklogMarkdown }`。

- **收益**：消除双份渲染漂移风险。
- **风险**：低（纯函数搬移）。搬移后跑 `npm test`。
- **工作量**：小。

### 2.2 O-5 后端无类型检查

- **定位**：`tsconfig.json` 仅 `include: ["ui"]`；`src-server` 是纯 JS（ESM）。
- **方案**（渐进、低风险）：
  1. 新增 `tsconfig.server.json`：

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": { "allowJs": true, "checkJs": true, "module": "ESNext", "moduleResolution": "Bundler", "types": ["node"] },
  "include": ["src-server"]
}
```

  2. `package.json`：`"typecheck": "tsc --noEmit && tsc -p tsconfig.server.json"`；`devDependencies` 加 `@types/node`。
  3. 关键模块（`store.js`/`metrics.js`/`llm.js`）优先补 JSDoc `@param/@returns/@typedef`，先让 `checkJs` 能通过再逐步收紧 `@ts-check`。
- **收益**：后端类型错误在 CI 即暴露；不引入运行时成本（仅类型）。
- **风险**：`checkJs` 初期会有较多报错；建议先 `checkJs` 打开但 `allowJs` 下用 `// @ts-nocheck` 逐文件开放，或先只对 2–3 个核心文件开启。
- **工作量**：中（渐进）。

### 2.3 O-6 测试 harness 重复 + 缺用例

- **定位**：`analyze-metrics`/`import-parser`/`metrics`/`sources` 各自定义 `assert/assert.equal/assert.deepEqual`（含 console），与 `store`/`literature-log`/`worklog-gen` 的 `node:test` 风格分裂。
- **方案**：
  1. 统一改用 `node:test` + `node:assert/strict`。
  2. 建立 `tests/helpers/assert.mjs`（若保留轻量 harness 则以此单一实现；去掉四处重复）。
  3. 补齐缺口：`log_work` 的 O-1 回归用例；`triage` 乱序条目水位线（O-12）边界用例。
- **收益**：断言逻辑单一化，`run-all.mjs` 正则收集可简化；补上真实 bug 的回归。
- **风险**：低；`run-all.mjs` 已按正则收集，迁移后确认文件名匹配。
- **工作量**：中。

### 2.4 O-7 MetricsChart 时区偏移

- **定位**：`ui/components/MetricsChart.tsx` 第 197 行 `fmtDateShort(new Date(t).toISOString().slice(0, 10))`。
- **影响**：东八区边界时刻 X 轴刻度标签可能显示成前一天（数据点 `date` 是本地/记录日期）。项目里 `SchedulePanel` 已正确（注释明确 avoid UTC+8），此处未对齐。
- **方案**：改用本地日期工具（`dates.ts` 已有 `fmt`）：

```ts
import { fmt } from '../lib/dates';
// 旧
label: fmtDateShort(new Date(t).toISOString().slice(0, 10))
// 新
label: fmtDateShort(fmt(new Date(t)))
```

- **收益**：刻度与数据点同源（本地时区），消除边界错位。
- **风险**：低（仅展示层）。
- **工作量**：约 5 分钟。

### 2.5 O-8 体系清单三处重复维护

- **定位**：`metrics.js SYSTEM_DEFS`、前端 `WorklogPanel.SYSTEM_PRESETS`、巡检 prompt 的 `system` 枚举（11 项，含"PEDOT/导电聚合物""无机/有机复合"斜杠写法）。
- **方案**（推荐 A，必要时 B）：
  - **A（轻量，推荐）**：在 `metrics.js` 导出 `SYSTEM_NAMES = SYSTEM_DEFS.map(s => s.name)`，并新增一个一致性测试（`tests/consistency.test.mjs`）：断言 `SYSTEM_NAMES` 与 `WorklogPanel.SYSTEM_PRESETS`（读取 TSX 文本或抽为共享常量）及 `worklog-triage.md` 中的枚举集合一致。测试失败即 CI 红，阻止三处漂移。
  - **B（彻底）**：建 `src-shared/constants.ts`（能被 `ui` 与 `src-server` 两端 import），三者统一从此导入；prompt 由代码生成（模板 + 注入枚举）。
- **收益**：改体系不再高风险地漏改其一。
- **风险**：A 无运行时改动只加测试；B 需处理前后端打包的共享模块解析（vite/esbuild 均需配置 alias）。
- **工作量**：A 小 / B 中。

## 3. P2 —— 可靠性加固与工程配置

### 3.1 O-9 id 生成不一致（部分无随机）

- **定位**：带随机后缀的 `log_work.newId`、`manage_schedule.newId`、`literature-log`、`SchedulePanel.newId`；**无随机**的 `commitDraft`（`work_${Date.now().toString(36)}`）、`CalendarView.addEvent`、`WorklogPanel.save`。
- **影响**：同毫秒连写两条会撞 id（低概率，但存在）。
- **方案**：抽 `src-server/server/ids.js`：

```js
export function newId(prefix) {
  return `${prefix}_${Date.now().toString(36)}_${Math.random().toString(36).slice(2, 7)}`;
}
```

后端各工具/`commitDraft`/`literature-log` 统一引用；前端在 `ui/lib/ids.ts` 同构实现，`CalendarView`/`WorklogPanel`/`SchedulePanel` 统一。多个文件以 `Math.random` 兜底，不依赖 `crypto`（现环境无）。
- **收益**：消除撞 id 隐患，风格统一。
- **风险**：低。
- **工作量**：小。

### 3.2 O-10 JSON 贪婪正则

- **定位**：`worklog-parse.js`、`llm.js`（`triageWorkEntry`、`parseScheduleBlock`）用 `raw.match(/\{[\s\S]*\}/)`。
- **影响**：LLM 输出含两个 JSON 对象时，贪婪匹配从首个 `{` 吞到末个 `}`，`JSON.parse` 失败返回 null（不阻塞但丢数据）。
- **方案**：写 `extractFirstJson(raw)`（非贪婪定位首个 `{`，用 depth 计数找到配对的 `}`）替换三处；或先试非贪婪 `/\{[\s\S]*?\}/`，parse 失败再回退贪婪。推荐前者更稳（兼容对象内嵌套 `{}`）。
- **收益**：提升 LLM 输出容错。
- **风险**：低（纯解析函数，可用单测覆盖）。
- **工作量**：小。

### 3.3 O-11 import-parser CSV 引号健壮性

- **定位**：`import-parser.js` 的 `detectDelimiter`/`splitRow` 不处理引号包裹字段中的内嵌逗号/转义。
- **影响**：对含 `"a,b"`、`"say ""hi"""` 的严格 CSV 会错裂。
- **方案**：实现 `splitCsvLine(line, delimiter)`（引号感知：遇 `"` 进入引号态，`""` 转义，`delimiter` 在引号外才切分），替换 `splitRow`；或在 README 明确"推荐 Excel 复制（TSV），不支持引号内嵌逗号"，把当前局限写进文档。
- **收益**：提升真实数据健壮性或明确边界。
- **风险**：低；需补 `tests/import-parser.test.mjs` 用例。
- **工作量**：小。

### 3.4 O-12 triage 乱序条目水位线跳过

- **定位**：`triage.js` 的 `pending` 用 `entries.filter(...).slice(-BATCH_MAX)`（取数组末尾），若存在 `createdAt` 早于 `reviewedAt` 的未巡检条目（乱序/补录），会被水位线永久跳过。
- **方案**：`pending` 先按 `String(e.createdAt)` 升序排序再 `slice(0, BATCH_MAX)`（取**最早**未巡检），或推进水位线时取「成功批次中 `createdAt` 的 max」并配合 `aiReviewedIds` 已做的同毫秒判重。
- **收益**：乱序补录不漏巡检。
- **风险**：需验证 `aiReviewedIds` 同毫秒判重逻辑仍正确（现有测试 T6 需保留）。
- **工作量**：小。

### 3.5 O-13 空 catch / createStore 重复实例

- **定位**：
  - 空 `catch {}`：`store.snapshot`/`pruneSnapshots`、`sources` 多处。
  - `createStore(ctx.dataDir)` 在 `index.js`/`routes/api.js`/`routes/export.js`/各工具各实例化一次。
- **方案**：
  1. 空 catch 至少补 `console.warn`（无法透传 ctx.log 的模块）或透传 `ctx.log?.warn`，便于排障。
  2. `createStore(dataDir)` 模块级 memoize（`Map<dataDir, store>`），同目录复用单例（当前无内存缓存，故安全）；或经 `ctx` 缓存注入。
- **收益**：可观测性提升 + 消除多实例隐患。
- **风险**：memoize 需确认无「不同调用方需独立状态」的场景（当前均同 dataDir，安全）。
- **工作量**：小。

### 3.6 O-14 前端数据层大面积 `any`

- **定位**：`Panel.tsx`/`Dashboard`/各 panel 的 `state: any`、`entries: any[]`、`api.getState(): Promise<any>`。`tsconfig strict` 对业务层形同虚设。
- **方案**：为 `state` 定义 `PluginState` 类型（在 `ui/api.ts` 或 `ui/types.ts`），`getState(): Promise<PluginState>`；界面组件用 `Record`/接口收窄。可先只给 `api.ts` 和 `Panel.tsx` 加类型，其余逐步。
- **收益**：前端类型安全实际生效，减少结构性错误。
- **风险**：改动面较大，需保持 `any` 为兜底渐进。
- **工作量**：中（可拆多次）。

## 4. 实施顺序与 CL 拆分建议

按「零风险正确性 → 类型/测试基建 → 打磨」三波推进，每波独立可回滚、独立核验。

### Wave 1（P0 正确性，优先）
- O-1 log-work 上下文重复追加（改 + 回归测试）
- O-2 版本号统一（package 单源 + UA 引用）
- O-3 prompts 脱节（删 3 处过时内容 + 跑 mock 测试 + 抽样 LLM）

### Wave 2（P1 工程/可靠性）
- O-4 export 渲染抽取专模块
- O-5 后端 `checkJs` 渐进类型（`tsconfig.server.json` + `@types/node`）
- O-6 测试 harness 统一 + 补用例
- O-7 MetricsChart 时区
- O-8 体系清单一致性测试

### Wave 3（P2 打磨，可选/低风险）
- O-9 id 统一（建共享 ids 模块）
- O-10 JSON 提取健壮化
- O-11 import-parser CSV 引号
- O-12 triage 乱序水位线
- O-13 空 catch 日志 / createStore memoize
- O-14 前端状态类型化（可拆多次）

## 6. 底线判断

- **必须先做**：O-1（逻辑 bug）、O-2（版本）、O-3（prompts 脱节，直接影响 AI 行为）。
- **价值最高**：O-5（后端类型化）与 O-6（测试 harness 统一）是长期维护性投资；O-8 一致性测试成本低收益稳。
- **其余为打磨**：无系统风险，按节奏推进即可。
